# 05. 今後の課題・ロードマップ

実装しながら明らかになった制約と、その現実的な解決方針をまとめる。「いつかやる」ではなく、何を試して何が難しかったかを具体的に残す。

## 道路の管轄自動判定(都道 / 区道の判別)

**現状**: 道路は既存の手打ちデータ4件(世田谷通り・目黒通り・明治通り・早稲田通り)のみ。それ以外の場所でピンを指しても道路としては一致しない(区フォールバックに留まる)。

**試したこと**:
- 国土交通省「国土数値情報」道路データ(N01)— 都道府県道/市区町村道の分類を持つ唯一の現実的な構造化データだが、実際に探索したところ生きたダウンロードリンクが見つからなかった(過去バージョンの仕様書ページはあるが配布ファイルが404)。
- 代替として国土数値情報N06(高速道路時系列データ)を確認したが、高速道路専用で対象外。
- 東京都建設局の道路台帳は2026年4月からWeb公開されているが、スキャン画像(平面図)のみで機械可読データではない。

**次の一手候補**:
- N01の生きた配布元が見つかれば、`RoadSegment`モデル(既にスキーマに用意済み)への取り込みスクリプトを`fetchParks.ts`と同じ設計で追加する。
- もしくは、実在する主要な都道・区道の名称・概略経路を個別に調査し、手打ちデータを段階的に増やす(現実的だが手間がかかる)。

## 公園データの残り8区

港区・目黒区・中野区・豊島区・北区・荒川区・板橋区・江戸川区は、東京都オープンデータカタログ上で「都市公園一覧」の標準CSVが見つからなかった。各区が独自ドメインで公開している可能性があるため、区の公式オープンデータページを個別に確認する余地がある。

## 担当部署の正式名称・連絡先

23区のうち世田谷・目黒・渋谷・中野の4区以外は、部署名を「(要確認)」付きの汎用ラベルで表示している。実在確認できたメールアドレスは1件も無い(各区とも問い合わせはWebフォーム経由)。正式名称・連絡先の確認は今後の課題。

## 管轄先への自動メール送信

`NotificationLog`に「誰宛に何を送る予定か」を記録する土台までは実装済み。実際の送信には以下が必要:

- メール送信サービス(SMTP/API)の契約・認証情報。
- 送信先アドレスの正当性の別途確認(行政の実在窓口に誤って送ってしまうリスクがあるため)。
- 行政側の受信可否・運用フローの合意。

## `AdminRole.jurisdictionScope`の実質化

現状は表示ラベルのみで、ダッシュボードの絞り込みには使っていない(どの行政職員も全提案を閲覧・操作できる)。担当区・担当部署でのアクセス制御を行うなら、`jurisdictionScope`を自由文字列から`Authority`への参照に変更し、ダッシュボードのクエリに`where`条件を追加する必要がある。

## 区境ポリゴンによる厳密な判定

現在の管轄判定は「近傍の施設・道路」または「GSI逆ジオコーディングの区名」による近似で、区境ポリゴンでのpoint-in-polygon判定はしていない。国土数値情報の行政区域データ(N03)は生存が確認できているため、将来これに置き換えることは可能(`PublicSite.ward`等は文字列のまま残しているため、置き換えの影響範囲は限定的)。

## PostgreSQL/PostGIS移行

現在はSQLiteで全件距離計算による近傍探索を行っている(`src/lib/geo.ts`)。データ量が今後大きく増える場合は、PostgreSQL+PostGISへの移行と`ST_DWithin`等の空間インデックスの活用を検討する。

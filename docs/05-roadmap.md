# 05. 今後の課題・ロードマップ

実装しながら明らかになった制約と、その現実的な解決方針をまとめる。「いつかやる」ではなく、何を試して何が難しかったかを具体的に残す。

## 道路の管轄自動判定(都道 / 区道の判別) — 解決済み(都民申告 + 住所ベースの区フォールバック)

**現状**: 新規提案フォームは「`PublicSite`(公園・図書館・道路)に登録済みの地点しか選べない」制約があり(`NewProposalForm.tsx`の投稿ボタンは`landType`が決まるまで押せない)、道路の手打ちデータは4件しか無いため、その4件以外の道路沿いではそもそも投稿できなかった。都道/区道を機械的に判別しようとする前に、この「投稿できない」こと自体が実害だった。

最初はOpenStreetMap Overpass APIでのライブ判定を試みたが、実装して検証したところ、この制約(PublicSite一致が無いと投稿自体できない)により**実際の投稿経路では絶対に呼ばれないコード**になってしまうと判明し、方針転換した。

**実際の解決策**: `LocationPicker.tsx`で、ピン位置の近くに`PublicSite`が見つからなくても、GSI逆ジオコーディングで住所(区)は取得できている場合、「この場所を公道として投稿する」ボタンを表示する。都民がこれを選ぶと`landType: "public_ward"`で投稿でき、`determineJurisdiction()`にその意思(`roadHint: true`)が渡り、区フォールバックで公園ではなく**区の道路担当部署**(`authority_road_区`、`seedAuthorities.ts`で23区分すでに投入済み)へルーティングされる。

都道/区道の厳密な分類はできないが、都民が申告した「公道である」という事実と、既に取得できている住所(区)だけで、実用上十分なルーティングができるという判断による。都道だった場合、区の道路担当から都建設事務所への庁内転送が必要になるが、区外への誤送信ではないため実害は小さい。

あわせて、区フォールバック(`determineJurisdiction()`のステップ2)が**道路沿いの提案でも常に公園担当部署に回してしまうバグ**を修正した(道路担当部署自体は既に全23区分投入済みだったが、一度も参照されていなかった)。

**試したこと(過去の記録として残す)**:
- 国土交通省「国土数値情報」道路データ(N01)— 都道府県道/市区町村道の分類を持つ唯一の現実的な構造化データだが、実際に探索したところ生きたダウンロードリンクが見つからなかった(過去バージョンの仕様書ページはあるが配布ファイルが404)。
- 代替として国土数値情報N06(高速道路時系列データ)を確認したが、高速道路専用で対象外。
- 東京都建設局の道路台帳は2026年4月からWeb公開されているが、スキャン画像(平面図)のみで機械可読データではない。
- OpenStreetMap Overpass APIでのライブ道路判定 — 技術的には動作したが、上記の理由(投稿フォームの制約により到達しない)で採用を見送った。

**`RoadSegment`モデルについて**: スキーマ上は存在するが(`geometry`カラムにポリラインを持たせる設計)、投入スクリプトが無く未使用のまま。将来、都道/区道の厳密な分類が必要になった場合の受け皿として温存する。

**残課題**: `LAND_TYPE_LABELS`(`public_ward`→「区立」)は元々「区立公園」等の施設向けの表記で、公道フォールバック時にもそのまま「区立」と表示される(「公道」等の道路向けの表記ではない)。所管部署名(`所管: 港区 道路管理担当課`)は正しく道路担当を指すため実害は無いが、表示の精度を上げるなら`LandType`に道路用の区分を追加するか、`Jurisdiction.authority.category`から動的にラベルを出し分ける改修が必要。

## 公園データの残り区 — 23区中18区まで解決、5区は未解決

当初、港区・目黒区・中野区・豊島区・北区・荒川区・板橋区・江戸川区の8区で、東京都オープンデータカタログ上の標準CSV(ファイル名パターン一致)が見つからなかった。個別にカタログを調査した結果:

- **荒川区**: 標準CSVは実在したが、ファイル名のローマ字表記が「toshitoritu**kouen**」ではなく「toshitoritsu**kouen**」(っ→つの表記がtu/tsuで揺れていた)だったため、正規表現が一致していなかった。正規表現を両対応させて解決。
- **目黒区**: 東京都のカタログとは別の共通オープンデータ基盤`data.bodik.jp`上に、「都立公園」「区立公園」が別々のデータセットとして公開されていた(Shift_JISエンコード)。`EXTRA_WARD_CSV_URLS`に個別登録して解決。
- **中野区**: 区独自のポータル`wagmap.jp`上に「公園配置図」が公開されていた(列名が「公園名」で標準の「名称」と異なる)。同じく個別登録して解決。列名の表記ゆれ・エンコーディング判定にも対応した。

残り**5区(港・豊島・北・板橋・江戸川)**は、東京都のカタログ・各区独自ポータルの両方を調査したが、機械可読な公園一覧データセットを発見できなかった。各区の公式サイトには公園に関するページ自体は存在するが(例: 江戸川区の公園写真ギャラリー等)、一覧CSV/構造化データとしては非公開と見られる。捏造はせず、これらの区は引き続き区フォールバック(住所ベースの担当部署ルーティング)で機能する。

## 担当部署の正式名称・連絡先

23区のうち世田谷・目黒・渋谷・中野・荒川・港・豊島・北・板橋・江戸川の**10区**は、各区公式サイトの組織案内ページを確認し、実在する部署名を採用した(公園データが無い5区のうち4区も、部署名自体は組織案内から確認できた)。北区は公式サイトのURL構成が変更されており(`city.kita.tokyo.jp`→`city.kita.lg.jp`)、直接のページ取得はできなかったため複数の第三者情報源で確認、要再検証としている。残り13区は正式名称を個別確認できていないため、部署名に「(要確認)」を付けて表示している。実在確認できたメールアドレスは1件も無い(各区とも問い合わせはWebフォーム経由)。

## 管轄先への自動メール送信

`NotificationLog`に「誰宛に何を送る予定か」を記録する土台までは実装済み。実際の送信には以下が必要:

- メール送信サービス(SMTP/API)の契約・認証情報。
- 送信先アドレスの正当性の別途確認(行政の実在窓口に誤って送ってしまうリスクがあるため)。
- 行政側の受信可否・運用フローの合意。

## `AdminRole`によるアクセス制御 — 解決済み

`AdminRole`に`authorityId`(`Authority`への参照、nullable)を追加し、ダッシュボード一覧(`admin/(protected)/page.tsx`)・詳細ページ(`admin/(protected)/[id]/page.tsx`)・ステータス変更(`[id]/actions.ts`)の3箇所で、自分の管轄(`Jurisdiction.authorityId`一致)以外の提案を閲覧・操作できないようにした。`authorityId`が`null`のアカウントは全域担当として従来通り全件を扱える。

`db:seed`ではAdminRoleを`authorityId`未設定のまま作成し(Authorityテーブルがまだ無いため)、`ingest:authorities`実行時にhandle経由で対応するAuthorityへ紐付ける(`seedAuthorities.ts`の`ADMIN_AUTHORITY_BY_HANDLE`)。`db:seed → ingest:authorities`の順で実行する必要がある(既存の初回セットアップ手順と同じ)。

## 区境ポリゴンによる厳密な判定

現在の管轄判定は「近傍の施設・道路」または「GSI逆ジオコーディングの区名」による近似で、区境ポリゴンでのpoint-in-polygon判定はしていない。国土数値情報の行政区域データ(N03)は生存が確認できているため、将来これに置き換えることは可能(`PublicSite.ward`等は文字列のまま残しているため、置き換えの影響範囲は限定的)。

## PostgreSQL/PostGIS移行

現在はSQLiteで全件距離計算による近傍探索を行っている(`src/lib/geo.ts`)。データ量が今後大きく増える場合は、PostgreSQL+PostGISへの移行と`ST_DWithin`等の空間インデックスの活用を検討する。

## 1. スコープ定義（ハッカソンMVP＝Phase 1）

原案のロードマップ「Phase 1: ハッカソン」を、実装できる粒度まで分解する。

### 1.1 作る（In Scope）

- 都民向け：地図上への提案投稿（位置情報＋写真＋カテゴリ＋説明文）
- 都民向け：ワンタップ・デジタル署名（LINEログインによる本人認証、二重署名防止）
- 都民向け：提案一覧・詳細・進捗ステータス表示
- 行政（管理）向け：受付済み提案の一覧・優先度スコア確認・審査ステータス変更ダッシュボード
- システム：署名数と最低限のオープンデータ（緑被率・人口密度など取得可能な指標）を組み合わせた優先度スコアリング（簡易版）
- システム：位置情報に基づく管轄自動判定（都立／区立／私有地の粗い切り分け。対象エリアは実データが取得できる特定区に限定 — [03-external-integration.md](./03-external-integration.md) 参照）

### 1.2 作らない・モックにとどめる（Out of Scope / Mock）

- マイナンバーカード（JPKI）連携 → 認定事業者経由の本格実装は行わず、画面上は「将来対応」のプレースホルダーのみ
- 実際の予算執行・補助金交付（金銭移動） → ステータスを「予算化決定」まで表現し、実際の会計処理・振込等は対象外
- 都・区市町村横断の正式な「合同査定委員会」ワークフロー → 承認ステータスの変更UIのみ実装し、実際の組織間合意形成プロセスは対象外
- 熱環境（表面温度）データ連携 → データの入手可否が未確定のため、取得できた場合のみ組み込む拡張スコアとする（[03](./03-external-integration.md) 参照）
- 多言語対応、アクセシビリティの本格対応（WCAG準拠） → MVPでは日本語のみ、基本的なセマンティックHTMLレベルに留める

## 2. ペルソナとユースケースフロー

### ペルソナ①：子育て世代の都民（30代）

**ゴール**：よく使う公園に日よけベンチが欲しい。

1. アプリ／Webを開き、地図上で公園にピンを立てる（区の選択や住所・キーワード検索でも位置指定可能）
2. 「公園設備」カテゴリを選び、理由（子どもが遊ぶ間休める場所がない等）と写真を添えて投稿
3. 投稿がSNS等でシェアされ、近隣住民が署名
4. 署名数が閾値（例：50筆）に到達すると「審査対象」ステータスに遷移する通知を受け取る
5. 進捗ページで審査状況・予算化決定・施工完了までを追跡

> **民間企業について**：GreenVoiceは都民のみが利用できるサービスであり、企業アカウント・企業による投稿は設けない（私有地・企業敷地への行政補助金交付は法律上できないため）。企業が関わりうるのは、都民の署名データをPark-PFI（公募設置管理制度）等の公募提案時の参考情報として活用する、間接的な形のみ（[00-concept.md](./00-concept.md) 4章、[07-impact-and-policy.md](./07-impact-and-policy.md) 3.2節）。

## 3. 機能要件一覧（画面単位）

| # | 画面 | 主な機能 | 優先度 |
| --- | --- | --- | --- |
| F1 | 投稿マップ | 地図上のピン表示（ジャンル別に色分け・クラスタリング）、新規投稿ボタン | Must |
| F2 | 投稿作成 | 位置指定（区市選択→施設名の予測変換で公有地を選択／地図クリック・ドラッグでの微調整／住所・キーワード検索、選択地点は住所ラベルを表示）、写真アップロード（必須）、カテゴリ・説明入力 | Must |
| F3 | 提案詳細 | 内容表示、署名ボタン、現在の署名数、進捗ステータスバー | Must |
| F4 | 署名 | LINEログイン、1提案1署名の重複防止、署名後の共有導線 | Must |
| F5 | マイページ | 自分の投稿一覧、署名した提案一覧、通知 | Should |
| F6 | 行政ダッシュボード（一覧） | 提案一覧、優先度スコア順ソート、管轄別フィルタ | Must |
| F7 | 行政ダッシュボード（詳細・審査） | 提案詳細、スコア内訳、ステータス変更（受付→審査中→採択→施工→完了） | Must |
| F8 | スコアリングバッチ | 署名数×オープンデータ指標から優先度スコアを算出・更新（**表示は行政ダッシュボードのみ**。都民向け画面には出さない） | Must |
| F9 | 管轄自動判定 | 投稿位置と対象エリアのGISデータを突合し、都立/区立/私有地を推定 | Should |
| F10 | 完了報告 | 施工後の写真・効果（緑化面積等）の共有、バッジ付与表示 | Could |
| F11 | 実現ショーケース | 完了（`completed`）ステータスの提案をマップ画面の目立つ位置に表示し、実際にアプリ経由で実現した事例を可視化する | Must |
| F12 | 一覧の並び替え | 提案一覧を「新着順」「署名が多い順」で並び替え | Should |

> F8の変更理由：都民向け画面にスコアを出すと「点数によって選別されている」という印象を与えかねないため非表示にした。行政側の判断根拠としての透明性は、進捗履歴（ステータス変更ログ）の公開で別途担保する。都民・行政それぞれに実際どの情報が渡るかの一覧は [08-admin-data-flow.md](./08-admin-data-flow.md) を参照。

> F2・F9の運用変更（実装反映）：当初想定していた「投稿者が公有地/私有地を自己申告し、行政が事後確認する」フローは、まず公共領域で管轄自動判定と審査フローを確立するため、**新規投稿を都・区市町村が管理する公有地（公園・図書館・道路等のマスタデータから選択）に限定**する形に変更した。これにより `land_type` は自己申告ではなく選択した施設から自動的に決定され、F9（管轄自動判定）は当面「施設マスタからの自動決定」で実質化している（GIS空間結合を伴う `gis_auto` への本格移行は [02-data-model.md](./02-data-model.md) 3章のとおり将来対応）。私有地緑化の再受付方針は [07-impact-and-policy.md](./07-impact-and-policy.md) 3.4節を参照。

## 4. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 対象環境 | スマートフォンWebブラウザを主、PCブラウザ（行政ダッシュボード側）を副 |
| 性能 | 地図表示・投稿一覧は3秒以内の初期表示を目標（デモ環境基準） |
| セキュリティ | 署名の重複防止、投稿写真の内容モデレーション（MVPでは目視運用も可） |
| データ保護 | 個人が特定できる情報（氏名・LINE ID等）は最小限のみ保持し、公開画面には表示しない。**実装**：`User.displayName`（本名）とは別に匿名の`User.handle`（例：都民-A1B2）を生成し、提案詳細・進捗履歴などの公開画面には`handle`のみを表示する。本名を閲覧できるのは行政ダッシュボードに限定する |
| 心理的ハードル | 想定される採択率は1割未満であることを前提に、投稿自体は気軽に行える体験にする（カジュアルな文言、ワンタップで選べるカテゴリボタン等）。「通らなくても声を届ける価値がある」ことが伝わるコピーを添える |
| 可用性 | ハッカソンデモ・実証実験規模（高可用性のSLAは設定しない） |
| 拡張性 | 対象エリア・オープンデータソースを増やせる設計（`03-external-integration.md` の統合方針に準拠） |
| ログ・監査 | ステータス変更履歴を保持し、行政ダッシュボードで確認可能にする（「民主的統制」の原則に対応） |

## 5. スコープ外事項の扱い方針

スコープ外とした機能（JPKI連携、実予算執行、正式な合議制ワークフロー）は、原案が掲げる「行政経営レベル3〜4」の実現に必要だが、**プロダクト単体では実現できず、東京都・区市町村の制度側の意思決定が前提**となる。そのため `05-roadmap.md` でPhase2・Phase3の"exit criteria"として明示し、プロダクトは常にその制度が発足した際に接続できるインターフェース（ステータス列、権限モデル）を残す設計とする。
